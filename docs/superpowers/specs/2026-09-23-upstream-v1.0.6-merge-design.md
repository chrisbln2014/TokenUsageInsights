**刻意保留、不改的例外**（日期本來就是本地時間）：
- **Cursor 的正常路徑**：`<timestamp>` 標籤本身就是本地時間，`cursor_date_from_timestamp` 直接截字串是正確的。第 9 點的備用路徑不算在這個例外裡。

### 4.2 解衝突原則

- 程式結構採用 upstream 的版本。
- 9 個寫入點寫進 `date` 的值（第 9 點則是寫進 timestamp 的值），一律改用本地時區的 helper。第 7 點直接改在 `insert_usage_entries` 裡；第 9 點移植到 `src/db/cursor.rs`。
- 第 8 點：upstream 的 `build_usage_entry_import_source_id` 改成 4 個參數。`record_date` 同時用在匯入 ID 和 `date` 欄位，只要改一處，兩處就會一致，而且都是本地日期。
- 保留 `5a88015` 新增的函式和測試：`date_from_timestamp_in_tz`、`local_date_from_timestamp`、`local_timestamp_string_from_system_time`、`rerun_local_timezone_date_backfill`。原本在 HEAD 側衝突區塊內的測試，要跟著搬到新的位置，例如 Cursor 的測試搬到 `cursor.rs`。

### 4.3 稽核（進入審查前的硬門檻）

1. **合併後，在解衝突之前**，先跑字串搜尋，預期會命中第 4、7、9 點。沒命中，代表對合併樹的理解有誤，要停下來查。
2. 解完衝突後，列出所有**正式程式碼**中寫 `date` 欄位的 SQL（INSERT 欄位清單含 `date` 的、`UPDATE ... SET date` 的），逐一追溯綁定值的來源。只允許三種：
   - 本地時區 helper。
   - 4.1 列明的例外。
   - **舊資料庫遷移**：`migrate_records` 會把舊資料庫的 `date` 原樣寫入，接著由 `migrate_old_databases` 呼叫 `rerun_local_timezone_date_backfill` 修正（合併樹 `db.rs:6680-6685`）。這條必須確認「寫入後一定會接著執行回填」這個順序還在。
   `#[cfg(test)]` 裡測試用的 fixture SQL 不在稽核範圍內。
3. 字串搜尋當第二道網：`get(..10)`、`get(0..10)`、`[..10]`、`[0..10]`、`split(['T'`、`Utc::now`、`DateTime<Utc>`。每一個命中都要歸類成「已修」或「明列例外」或「不寫 date／timestamp 欄位」。
4. 稽核結果不乾淨，不得進入節點審查。

### 4.4 測試

- 9 個寫入點各一條測試，第 7 點的 mcode 另加一條，共 10 條。原本就有的測試可以沿用，搬到新位置即可。
- 同步函式內部寫死用 `chrono::Local`，而 Windows 上的 `chrono::Local` 不看 TZ 環境變數，所以測試沒辦法指定時區。規則如下：
  - 純函式（`date_from_timestamp_in_tz`）用固定偏移測試，在任何機器上都有效。
  - 寫入點測試用「本地時間 00:30」構造資料，斷言寫進去的是本地日期。**這些測試必須在 UTC+8 的機器（本機）上跑，才算驗收有效。** 本地偏移為 0 時，這些斷言沒有偵測力，驗收報告要記錄跑測試時的本地偏移。
- 突變驗證：逐點把寫法改回 UTC，對應的測試必須紅，而且要紅在那一條斷言上。每個突變都記錄「預期紅在哪個 檔:行」和「實際紅在哪裡」。至少一個突變由審查員指定。

### 4.5 回填

- **固定新增**一個冪等回填，標記是 `migration:local_timezone_date_v2`，做法與 v1 相同（只在算出的新值和既有值不同時才 UPDATE）。v1 的名單不動。
- v2 的範圍是 `assistant_type = 'mcode' OR import_batch_id IS NOT NULL`：
  - **mcode**：理由見下方。
  - **所有匯入資料，不分助理**：`5a88015` 修復前的匯入路徑，會對任何助理的匯入資料截取 UTC 日期；v1 只涵蓋 7 個助理，所以 Cursor、Antigravity 的**匯入**資料仍可能是錯的日期。本機同步進來的 Cursor、Antigravity 資料依設計是本地時間，`import_batch_id IS NULL` 會把它們排除，v2 不會碰到。
  - 已經被 v1 修好的匯入資料，v2 重算的結果相同，不會更新。
- 為什麼不看快照查詢結果決定：匯入函式可以接受任何 assistant 字串，從「查快照」到「換版」之間，隨時可能有一筆 mcode 被匯入，查到 0 筆不代表換版時也是 0 筆。固定新增 v2 的成本很低：只掃 mcode 的列加上所有匯入的列，只執行一次，也不必分兩種情況處理。實際資料驗證時，要記錄這兩類各掃了幾筆、更新了幾筆。
- 測試要涵蓋四種情況，每種都從「已有 v1 標記」的資料庫開始：
  1. 沒有 mcode 資料、也沒有匯入資料：v2 會執行，而且不改動任何列。
  2. 有一筆 UTC 錯日的 mcode 資料：v2 會把它修正。
  3. 有一筆 UTC 錯日的**匯入** Cursor 資料：v2 會把它修正。
  4. 有一筆**本機同步**的 Cursor 資料，時間戳帶其他時區偏移：v2 不會改動它。
- 同步進來的新 mcode 資料不靠回填：只要合併後的版本第一次執行時，第 7 點就已經修好，這些資料從一開始就是對的。
- upstream 裡會重建資料的遷移，都走同步路徑：`grok_parser_v8` 整批重新解析走第 6 點；Cursor 模型簽章快取重設後會清掉 `cursor:%` 同步狀態並重新同步，走第 9 點。codex 身分遷移只做 UPDATE 和 DELETE，不會重新插入資料。所以只要 9 個寫入點都修好，重建出來的資料就是對的。

### 4.6 upstream 新測試在 UTC+8 下失敗時

修改測試，改用固定偏移，或改成跟本地偏移無關的斷言。不得移除時區修復。

5. **實際資料驗證**（全程不碰正式資料夾，只讀取正式資料庫一次）：
   1. 用唯讀連線（`file:...?mode=ro`）對正式資料庫執行**一次** `VACUUM INTO`，在一個固定的絕對路徑（不是 scratchpad——scratchpad 綁定 session ID，`/clear` 後新 session 接手會算出不同路徑，誤判成「還沒開始」而第二次讀取正式資料庫）產生一份快照，再把它複製成兩份，並核對兩份的雜湊值相同。不能分別執行兩次 `VACUUM INTO`：正式看板每 5 秒會同步寫入，兩次的時間點不同，得到的資料就不同。
   2. 在分身資料夾分別建置 `5a88015`（基準）和合併版，把執行檔**複製到上述固定路徑**再執行。兩個執行檔各指向一份快照（`INSIGHTS_DIR`），使用 18000 以上的埠，**同時啟動**。來源路徑的環境變數要逐一明確指定，兩邊的值完全相同：所有來源目錄（`ANTIGRAVITY_DIR`、`COPILOT_DIR`、`COPILOT_APP_DIR`、`CODEX_DIR`、`CLAUDE_DIR`、`CURSOR_DIR`、`GROK_DIR`、`PI_DIR`、`OMP_DIR`、`MUSE_DIR`、`MCODE_DIR`），加上兩個獨立的狀態檔 `CURSOR_STATE_DB`、`MCODE_STATE_DB`。來源 log 在執行期間仍會新增，但新增的內容屬於今天，已由「排除今天」的規則處理。
      執行前後都要確認家目錄下的舊版資料庫路徑（`~/.token-usage-insights/`、`~/.gemini/antigravity-cli/`、`~/.copilot/`、`~/.codex/` 下的 `*token_insights.db` 或 `token_usage_insights.db`）仍然不存在。`migrate_old_databases` 只有在這些檔案存在時，才會搬移或改名。
   3. **時區日期檢查**（合格標準：**未解釋的命中為 0**，同時輸出每一類的筆數）。合併版同步後，執行下方「完整查詢」這一段；(a)～(c) 的說明是它的分類依據。
      - **(a) 有時區標記的 timestamp**（結尾是 `Z` 或 `±HH:MM`）：`date` 必須等於 `strftime('%Y-%m-%d', timestamp, 'localtime')`。
        ```
        SELECT assistant_type, source_kind, count(*) FROM usage_entries
        WHERE NOT (assistant_type = 'cursor' AND import_batch_id IS NULL)
          AND (trim(timestamp) LIKE '%Z' OR trim(timestamp) GLOB '*[+-][0-9][0-9]:[0-9][0-9]')
          AND date <> strftime('%Y-%m-%d', trim(timestamp), 'localtime')
        GROUP BY 1, 2
        ```
        Antigravity、Copilot hook 的時間戳也屬於這類，照樣檢查。它們的日期取自本地檔名，理論上應該一致；有命中要逐筆解釋，例如跨午夜寫入。
        **本機同步的 Cursor 資料**（`assistant_type='cursor' AND import_batch_id IS NULL`）不套用 (a)：它的正常路徑依設計直接截取時間戳的前 10 碼，時間戳可能帶其他時區的偏移（`cursor.rs:23-42`）。這類另外檢查 `date = substr(trim(timestamp), 1, 10)`，不相符的必須是 0 筆。**匯入的 Cursor 資料**走第 8 點的本地時區寫法，所以跟其他來源一樣套用 (a)、(b)、(c)。
        **完整查詢**（取代上面的示意 SQL）。分類的優先順序固定，每一列只會落在一個類別：
        1. `invalid`：時間戳無效。
        2. `cursor_local`：本機同步的 Cursor 資料。
        3. `tz_marked`：時間戳帶時區標記。
        4. `bare`：時間戳沒有時區標記。

        Rust 的 `str::trim()` 會去掉空白、Tab、換行，SQLite 的 `trim(x)` 只去掉空白，所以這裡明確指定要去掉的字元。
        ```
        WITH t AS (
          SELECT assistant_type, source_kind, import_batch_id, date, timestamp,
                 trim(timestamp, ' ' || char(9) || char(10) || char(13)) AS ts
          FROM usage_entries
        ), c AS (
          SELECT *, CASE
            WHEN timestamp IS NULL OR ts = '' OR date = 'unknown'
                 OR strftime('%Y-%m-%d', ts) IS NULL                       THEN 'invalid'
            WHEN assistant_type = 'cursor' AND import_batch_id IS NULL     THEN 'cursor_local'
            WHEN ts LIKE '%Z' OR ts LIKE '%z'
                 OR ts GLOB '*[+-][0-9][0-9]:[0-9][0-9]'                   THEN 'tz_marked'
            ELSE 'bare' END AS cls
          FROM t
        )
        SELECT cls, assistant_type, source_kind, count(*) AS n,
               sum(CASE
                     WHEN cls = 'tz_marked'    AND date <> strftime('%Y-%m-%d', ts, 'localtime') THEN 1
                     WHEN cls = 'cursor_local' AND date <> substr(ts, 1, 10)                     THEN 1
                     WHEN cls = 'bare'         AND date <> substr(ts, 1, 10)                     THEN 1
                     ELSE 0 END) AS mismatched
        FROM c GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;
        ```

        判定標準：
        - `tz_marked`、`cursor_local` 的 `mismatched` 必須是 0；不是 0 的話，每一筆都要逐筆解釋。
        - `bare` 對照的是程式的回退行為：解析失敗時保留前 10 碼。所以它的 `mismatched` 也必須是 0。另外要列出每個來源的樣本，確認沒有時區標記是合理的，例如 Cursor 匯入資料或舊格式。
        - `invalid` 每一類都要找到原因，例如 mcode 缺少時間戳時存成空字串（`mcode.rs:286-288`）。
      - **(b) 無效的 timestamp**（NULL、空字串、`date='unknown'`、`strftime(...)` 為 NULL）：列出來源與筆數，每一類都要找到原因（例如 mcode 缺少時間戳時存成空字串，`mcode.rs:286-288`）。SQL 裡跟 NULL 比較不會命中，所以這一類必須單獨查。
      - **(c) 沒有時區標記的 timestamp**：SQLite 會把它當成 UTC 換算，程式卻直接截前 10 碼，兩者算法不同，所以**不能**套用 (a) 的比對。改成列出來源、筆數和樣本，逐類確認是 Cursor 正常路徑（本地時間），或是匯入時帶進來的格式。
      Cursor 備用路徑沒辦法從資料庫判斷，因為資料庫沒有記錄哪一列走過備用路徑。改由 4.4 第 9 點的測試驗收：用一份沒有 `<timestamp>` 的固定 fixture，並固定檔案 mtime，明列輸入值以及預期的 timestamp 和 date。
   4. **token 比對**：先確認比對鍵在兩邊都沒有重複，再用 (assistant, source_kind, source_dir_key, session_id, turn_no, usage_identity) 逐筆比對兩邊的 token 數與 `date`，比對方式是多重集合比較（multiset）。`source_dir_key` 是 Copilot App 唯一索引的一部分（upstream `db.rs:902-909`），缺了它會配錯。

      **codex 的 `usage_identity` 在兩邊天生就不一樣，比對前要先換算，不能直接拿來當比對鍵的一部分。** `5a88015` 完全沒有 codex rollout 身分的概念，codex 列的 `usage_identity` 一律是空字串（INSERT 欄位清單裡根本沒有這個欄位）。upstream 新增的 `codex_rollout_identity_v1` 遷移會把它們改標成 `rollout=<檔名去掉 .jsonl 副檔名>`（只在 `transcript_path` 的檔名以 `rollout-` 開頭時才套用，upstream `db.rs:3860-3875`），匯入的 codex 列也一併改標。比對 codex 列之前，先把基準版（old）那邊的 `usage_identity` 換算成預期值，才能跟合併版（new）配對；換算不出來的（檔名不是 `rollout-` 開頭）維持原值。

      排除今天，不比成本（upstream 調整過定價）。每一筆差異都要歸因，並附上筆數。可以接受的原因有三類：
      - **某個 upstream 遷移**：例如 codex 孤兒或重複匯入的刪除、`grok_parser_v8` 重新解析、跨來源去重、上面提到的 codex 身分改標。
      - **執行期間新寫入的來源 log**：兩個版本同時讀取正在變動的 log，可能讀到不同的時間點。必須用「差異列的 timestamp 晚於兩版啟動時間」或「該 session 的 transcript 在執行期間有修改（mtime）」來證明。
      - **v2 時區回填**（4.5 節）：基準版（`5a88015`）只有 v1 回填，合併版另外跑 v2，會修正 mcode 與所有匯入資料的 `date`。這類差異必須逐列對上時區日期檢查（第 3 點）已經匯出的「應更新筆數」清單，日期改動方向要跟 `new_date` 一致，其餘欄位（尤其 token 數）必須完全相同，不能只是「剛好也叫 v2 就放行」。

      不能有無法解釋的差異。來源 log 不另外凍結：這類差異會以誤報的形式出現，不會讓 bug 漏網，而歸因的要求就能把它和真正的問題分開。
   5. **冪等**：合併版重新啟動一次，今天以外的資料要完全不變。
   6. 合併版的 `--export-snapshot` 要匯出 10 個助理。
   7. **瀏覽器實測**合併版：`/api/version` 回傳 `1.0.6`，畫面顯示 `v1.0.6`；10 個助理的日報、月報、年報都能載入；console 零錯誤。

## 9. 已排除的路

- 直接 `feature` ← upstream 一步合併：會打破 `improve` 作為乾淨 upstream 整合層的分層。
- 逐一 cherry-pick 45 個 commit：數量多，又含 merge commit，容易遺漏。
- 在主資料夾合併：正式看板和上傳排程會立刻讀到還沒合併完的檔案。
- 只用字串 grep 稽核：抓不到 `split` 這類寫法（匯入路徑就是實例）。
- 「新舊版總數必須一致」：upstream 有刻意刪除重複列、重新解析的遷移，總數本來就可能改變。
- 直接複製正在使用中的資料庫檔：可能複製到寫到一半的狀態。
- 在正式安裝目錄執行任何執行檔：會被判定為正式安裝，干擾正式服務。
- 用 rerere：兩段合併沒有重複的衝突。
- 以為「衝突解完＋測試綠」就代表時區修復都在：第 4、7、9 點是無衝突退化。
- 以為測試可以指定時區：Windows 上的 `chrono::Local` 不看 TZ 環境變數。
- 依快照查詢結果決定 mcode 回填怎麼做：查詢和換版之間可能有新的匯入進來。
- 分別執行兩次 `VACUUM INTO`：兩份快照不是同一個時間點。
- 把 Cursor 放進 localtime 比對：它的正常路徑依設計不做時區換算。
